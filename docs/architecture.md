# Playlist Wizard architecture

## Single-file JavaScript setup

Wizard uses the identical JavaScript setup engine, Windows adapter and builder as Sync. The builder embeds only this add-on's allowlisted public files in one `.mjs`; official Node.js 24+ is required first. Setup retains installed data locations, validates all pinned tools and extracted Essentia files, creates compatible managed receipts and integrates regular rbxport shortcuts. Both install orders preserve the independent companion. Windows API helpers receive JSON over stdin with no script-file dispatch or execution-policy override. Setup never launches rbxport or analyzes music. Per-product/shared locks and a program-file journal protect concurrent updates and restore failed changes. Optional EXE builds remain separately signing-gated.

The current development startup uses the same self-contained `scripts/Start-Rbxport.mjs` as Sync. Shortcuts target unchanged official Node.js after checksum and OpenJS publisher-signature verification. A shared checksum-named runtime survives removing either add-on; the minimized parent dispatches a hidden worker. A brief minimized console is possible. No native startup EXE is built and no PowerShell script files are dispatched at startup; a fixed read-only Windows process inventory still uses PowerShell. Each service is launched directly with its original saved-data directory and exact host PID. Paired sidebar readiness, independent failures, bounded launch locking, abandoned-owner recovery and close/reopen cancellation remain enforced. Errors open private diagnostic text in Notepad. Runtime signing is not a signature of our JavaScript or proof of complete Smart App Control compatibility. Setup signing and exact-candidate validation remain separate release gates.

Wizard retains its independent managed installation receipts, existing-copy/data discovery, hash-checked removal and compact Installation confirmation. The paired API rejects uninstall while generation/creation is active and locks further actions during helper startup. Historical native-launcher versions are described below.

Version 0.1.1 uses the identical public `RbxportLauncher.cs` and PowerShell helpers shipped by Sync 0.11.4. Configuration compiles a console-free Windows shortcut target with the installed .NET Framework compiler, caching source/output SHA-256 hashes. Both native-to-helper and helper-to-add-on dispatch use `UseShellExecute=false` and `CreateNoWindow=true`. Wizard background startup confirms its sidebar button before returning. The shared native launcher records local status/errors and displays startup failures; it waits for launcher processes, not persistent descendants. Source remains in the ZIP; compiled runtime binaries do not. The generated launcher is unsigned and subject to Windows application-control policy.

Playlist Wizard is independently runnable and installable. Runtime imports stay inside this directory. It never opens Playlist Sync state, starts sync jobs or calls acquisition providers. Both add-ons can connect to the same opt-in host automation port using distinct CDP bindings, sidebar IDs and globals.

`Configure-Rbxport-Startup.ps1` registers Wizard with the neutral shared launcher and sets the user's `RBXPORT_DEVTOOLS_PORT=43822`. The original rbxport Desktop/Start Menu shortcuts start the selected host once, then both enabled independent services. Both distributions carry identical Startup, HostShortcuts and Start-Rbxport helpers; configuration under `%LOCALAPPDATA%\rbxport-addons` holds registrations, the host executable, original environment setting and hash-checked original shortcut backups. The launcher lives there independently of either installation. Disabling one add-on preserves the other; disabling the last restores unchanged shortcuts and the original port unless independently changed. Conventional separate add-on/sign-in shortcuts are removed after command/package checks. Each service follows the exact host PID, cancels and closes on confirmed exit, and waits for the previous session on a quick reopen. No pairing token, library state or runtime dependency is shared. The host executable is unchanged.

Every host operation establishes the active desktop library identity. USB operations additionally re-enumerate the pinned volume ID, mount and library format. Source snapshots include exact IDs, metadata and file stat stamps. Writes refuse changed snapshots. Device IDs are never passed to desktop membership commands. Missing capabilities have no guessed-path fallback.

Review loading is a serialized `cue` operation. It accepts a track only from the current saved draft, rechecks its file stamp, obtains its full current native row by exact ID in the pinned collection/device source, and checks path/duration/missing state. `host-player.mjs` uses the version-pinned TrackTable `onLoadTrack('a', row)` UI callback obtained from React's rendered fiber props; this is a private host UI contract, not a permanent extension API. It requires an unambiguous callback, visible Player 1 and the expected player metadata hook. An unsupported view fails without a direct-engine or guessed-path fallback. Desktop rows that would trigger the host's automatic analysis are refused. The real Pause control clears any deferred play intent before replacing a playing deck. Native load ID, displayed track ID, loaded/paused flags and a confirmed start-position seek establish success; unknown outcomes remain errors. Player 2 and library content are not edited. The cooperative lease excludes overlapping add-on writes/loads, while generation and creation remain blocked until the cue settles. No cue action persists a draft edit or changes an energy correction.

The host's `device_playlist_edit` source contract accepts create/add. Output uses a fresh target and append batches; readback verifies that the host preserved exact order. No device remove/delete command, automatic import, full USB synchronization or in-place reorder is exposed by Wizard.

The neutral `window.__rbxportAddonWriteLease` guards each native mutation while its promise is pending. The accompanying Sync bridge patch observes the same lease. It deliberately does not expire during a pending native promise. It is not an atomic source-snapshot/write transaction or protection against an old add-on/manual host edit. Native errors and uncertain results remain explicit.

Write journals bind one draft to one target. Unknown creation outcomes block blind recreation. Known targets can resume only when their readback is an exact prefix of the planned IDs. Completed drafts are idempotent. On interruption no playlist or music is automatically deleted.

Analyzer cache keys include library/device namespace, track ID, backend and version; file stat stamps invalidate entries. Manual corrections retain their original, backend-independent keys. Basic can reuse its original cache entries. No raw decoded audio is saved. All local paths/cache records remain in private state; the panel receives only the features needed for review. File stat equality is a fast cache check, not a content/provenance proof.

Uncached analysis revalidates the pinned library/device identity before and after decoding and accepts a cache entry only when its file stamp still matches the snapshot. Pools up to 10,000 tracks can be analyzed independently of the 500-song output limit. `analysis-queue.mjs` caps Essentia at two track tasks (one on smaller/memory-constrained machines); Basic stays serial. Result slots retain source order regardless of completion order. An abort or fatal error stops dispatch and drains siblings before generation settles, so no worker continues caching after cancellation. Completed, validated entries remain available on retry.

Before audio analysis, eligibility separates unavailable files, unknown/invalid durations and recordings over 30 minutes from a subset request. Song-count/duration modes disclose each exclusion count; the draft preview shows them directly. Autosort retains its complete-membership promise and reports blockers with sample titles and corrective options. Locked ineligible songs cannot be dropped. The optimizer repeats duration eligibility for direct callers, and independent output validation rejects an invalid selected duration. Source snapshots still include excluded tracks so later changes invalidate a pending output.

The current beam search keeps 12 states and up to eight expansions per state, yields between positions and has a 15-second budget. Autosort includes every candidate; subset search caps its shortlist at 600 and discloses it. A failed bounded search is reported as no draft found, not a proof of mathematical infeasibility. Curve cost averages intro/body/outro energy mismatches at excerpt midpoints on the elapsed set timeline, with a full possible mismatch for unknown energy. Manual corrections use a single corrected track estimate. Final-runtime section targets feed chart dots and curve review; an opening warning stays visible outside collapsed notes. These remain soft energy preferences and review thresholds, without weakening hard tempo/key, count, duration or lock requirements.

Essentia.js is the default requested-analysis backend. Complete FFmpeg decoding feeds a bounded collector at 44.1 kHz; at most three 30-second windows reach an isolated, cancellable worker. Essentia measures danceability, onsets, dynamics/loudness, centroid and bass ratio for every analyzed track. Rhythm/key estimates run only for the corresponding missing host metadata. Cache entries record attempted estimates, so a later metadata gap cannot silently reuse an insufficient entry. The descriptor version remains compatible with previous complete-estimate caches. Sampled intro/body/outro energy fits the curve and sampled outro/intro features add soft transition costs. Missing runtime never silently selects Basic. Measured duration mismatches block generation. Details, scoring weights and limitations are in [audio analysis](audio-analysis.md).

Basic retains the earlier complete-file envelope/brightness/bass/crest/activity heuristic as an explicit alternative. Both energy mappings remain experimental. Neither backend optimizes cue-region pairs, detects vocals or establishes musical phrase boundaries. Calibration and independent listening evidence are required before claiming musical reliability. Adding an agent, trained features and transition audition remains future work.
